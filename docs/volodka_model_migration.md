# Перенос физической модели Volodka

## Что меняется для оператора

Обычный запуск GUI через `scripts/run_gui.ps1`, `scripts/run_gui.sh` или
`python -m robot_human_interface` сохраняется. GUI и основной CLI используют
физический профиль `volodka` по умолчанию. Интерфейс, каталог эталонов,
пользовательские файлы, камера, MediaPipe, калибровка, timeline и запись опытов
не заменяются приложением из `humanoid_model`.

Перенесены физический паспорт, модель тела и CAD-геометрия, а не отдельная
PyQt5-мастерская и не её планировщик ходьбы. Команды по-прежнему формируются
цепочкой видео/камера → скелет → retargeting → существующий контроллер → MuJoCo.
Отображение суставов и параметры контроллера адаптированы к новой модели.
Демонстрационная ходьба из исходного проекта не является встроенным режимом
нашего GUI после этого переноса.

У Volodka 21 физическое тело, 20 шарнирных суставов и суммарная масса
3,0942 кг. Паспорт исходного проекта связывает массы и центры масс с CAD.
Оригинальный чертёж в переданном архиве отсутствует: перенос сохраняет
заявленное происхождение параметров, но не подтверждает его независимым
измерением. Звенья ноги между основными осями имеют длину по 0,08 м;
предварительный масштаб прежней Unity-модели не используется.

## Файлы и профили

| Назначение | Новый профиль Volodka | Прежний профиль |
|---|---|---|
| Идентификатор | `volodka` | `unity_legacy` |
| Свободная база | `models/volodka/scene_free.xml` | `models/humanoid/scene_free.xml` |
| Диагностическая опора | `models/volodka/scene_fixed.xml` | `models/humanoid/scene_fixed.xml` |
| Суставы | `config/joints_volodka.yaml` | `config/joints.yaml` |
| Баланс | `config/balance_volodka.yaml` | `config/balance.yaml` |

Старая папка `models/humanoid` сохранена. Низкоуровневые конструкторы симуляции
и retargeting сохраняют прежние defaults для совместимости существующего
Python-кода; собранный production-pipeline явно передаёт выбранный профиль.
Поэтому вызов отдельного `HumanoidSimulation()` без профиля — не доказательство
того, какую модель использует GUI.

Исходный экспорт лежит отдельно от адаптированных runtime-сцен:

- `models/volodka/source_scene.xml` — исходные координаты/имена/нулевая поза;
- `models/volodka/physical_snapshot.json` — паспорт, единицы и provenance;
- `models/volodka/import_provenance.json` — SHA-256 экспорта и исходных модулей;
- `models/volodka/meshes/` — 21 исходный STL и проверяемый CAD-manifest.

Совпадение числа суставов не означает совпадения порядка, знаков и нулей.
Адаптер сохраняет публичные legacy-имена и порядок команд нашего pipeline,
согласуя их с осями новой модели. Это программная совместимость симуляции,
а не аппаратная калибровка.

## Ограничения и реальный робот

- Инерции приближены стержнями и коробками; CAD-меши служат визуализации,
  а не точному расчёту массы и инерции.
- Контакты с полом заданы отдельными оболочками и площадками стоп.
  Самостолкновения звеньев в перенесённой физической модели отключены,
  как в upstream; проверка пола не заменяет проверку столкновений частей робота.
- Встроенный позиционный привод с пределом 1,5 Н·м — численный эталон.
  Он не идентифицирован по AR-S430-01 и не описывает измеренный люфт,
  нагрев, токи, питание и задержки реального привода.
- Трение и ограничения суставов требуют проверки на реальном образце.
- Свободная сцена допускает падение. Диагностическая fixed-сцена поддерживает
  корпус и не предназначена для оценки устойчивой ходьбы.
- В одноопорной фазе видео выбирает поднимаемую ногу, а её траектория задаётся
  отдельным CAD-профилем. Дополнительное подмешивание произвольной позы ноги
  отключено: прежний профиль мог приводить к касанию пола корпусом сервопривода.
  Это не режим копирования произвольных ударов ногой или полноценной ходьбы.
- Успешное копирование движения в симуляции не гарантирует его выполнимость
  на железе; прежние численные результаты Unity-модели здесь неприменимы.

**Для `volodka` включение отправки на физический робот заблокировано**:
соответствие углов реальным моторам ещё не проверено на аппаратном стенде.
Legacy WebSocket-протокол не менялся, но это не делает новые углы автоматически
пригодными для аппаратуры. Возврат к старому профилю не является обходом,
разрешающим испытание новой модели; для испытаний нужны отдельная проверка
сопоставления суставов, безопасный стенд и физический E-stop.

## Как воспроизвести прежний pipeline

Из корня проекта в PowerShell:

```powershell
.\.venv\Scripts\python.exe -m robot_human_interface.app.teleop --source synthetic --model-profile unity_legacy
```

В Ubuntu:

```bash
.venv/bin/python -m robot_human_interface.app.teleop --source synthetic --model-profile unity_legacy
```

Для новой модели замените `unity_legacy` на `volodka` или опустите аргумент.
Выбор источника видео/камеры и остальные CLI-параметры сохраняются.
Графический переключатель физического профиля этим переносом не добавляется.

## Перенос на другой компьютер и пересборка ресурсов

Обычному запуску нужны только репозиторий и его зависимости. Копировать исходный
`humanoid_model` в Downloads, устанавливать PyQt5 или менять `PYTHONPATH`
не требуется. XML используют относительные пути к мешам; конфигурации и модель
разрешаются через `ResourceLocator`, а не относительно текущей директории.
Окружение Windows/Ubuntu 24.04 подготавливается штатными setup-скриптами и
`uv sync --locked`; новые тяжёлые зависимости не добавляются.

Переносите весь репозиторий, включая `models/volodka/meshes`, конфигурации,
`assets` и lock-файл. `.venv` с другого компьютера переносить не нужно.
`MANIFEST.in` включает STL/XML/JSON и конфигурации в source-distribution.
Это не обещание готового portable-приложения или ресурсной упаковки обычного
wheel: текущий поддерживаемый способ остаётся запуском из репозитория/venv.

Перегенерация состоит из двух стадий, которые не нужны при обычном запуске.
Первая нужна только при обновлении исходной физической модели и требует
проверенного upstream-архива:

```powershell
.\.venv\Scripts\python.exe -B tools/import_humanoid_model.py --source C:\path\to\humanoid_model
```

Импорт проверяет SHA-256 STL, сохраняет каноническую сцену, паспорт и сведения
о происхождении. Команда выполняет Python-код из upstream-архива: неизвестный
архив нельзя считать безопасным только потому, что это «импорт модели».

Вторая стадия строит runtime-адаптер уже из локального экспорта и не требует
Downloads или upstream Python-модулей:

```powershell
.\.venv\Scripts\python.exe -B tools/build_volodka_adapter.py
```

В Bash замените путь к Python на `.venv/bin/python`. После регенерации следует
проверить изменения в Git и повторить модельные/pipeline-тесты. Изменение
паспорта или осей upstream требует повторной проверки адаптера, а не только
успешной компиляции XML.
